Overview

This contract enables a one-way swap from legacy xBTC (Wrapped Bitcoin, SIP-010) to sBTC at a 1:1 ratio. The swap is semi-custodial: users deposit xBTC and receive IOU tokens (swapping-xbtc-v4). A custodian periodically sweeps the xBTC, bridges it to BTC, deposits the BTC into the sBTC bridge, and the resulting sBTC flows back to the contract. Users then burn their IOUs to claim sBTC.

The contract uses Clarity 4's as-contract? with explicit with-ft allowances — a significant security improvement over pre-Clarity 4 patterns. However, the custodial model introduces trust assumptions and timing risks that are inherent to the design.

Architecture

  • Deposit: deposit-xbtc — user sends xBTC to the contract, receives 1:1 swapping-xbtc IOU tokens
  • Withdraw (pre-swap): withdraw-xbtc — user can reclaim xBTC before custodian sweeps, burning IOUs
  • Custodian sweep: init-unwrap — operator sends all xBTC to the custodian for BTC bridge processing
  • Claim: claim-sbtc — user burns IOUs and receives sBTC (partial claims allowed if sBTC < IOUs)
  • Excess recovery: withdraw-excess-sbtc — permissionless; sends any sBTC above IOU supply to the swap wallet
  • Enrollment: enroll — deployer can enroll contract in dual stacking or similar programs

Lifecycle

  1. Deployer calls initialize to set custodian and operator (one-time)
  2. Users call deposit-xbtc to deposit xBTC, receiving IOU tokens
  3. Operator calls init-unwrap to sweep all xBTC to custodian (~every 2 weeks)
  4. Custodian bridges xBTC → BTC → sBTC deposit (off-chain)
  5. sBTC arrives at the contract; users call claim-sbtc to redeem IOUs

Findings

HIGH

H-01: enroll accepts arbitrary trait contracts, enabling fund extraction

Location: enroll function

Description: The enroll function accepts any contract implementing enroll-trait:

(define-public (enroll
    (enroll-contract <enroll-trait>)
    (receiver (optional principal))
  )
  (begin
    (asserts! (is-eq tx-sender deployer) err-unauthorized)
    (as-contract? () (try! (contract-call? enroll-contract enroll receiver)))
  )
)

The as-contract? call uses an empty allowance (), meaning the callee executes as the swap contract but without explicit token allowances. However, the called enroll function could itself call other functions that transfer tokens or STX owned by the swap contract. While as-contract? with empty allowances doesn't directly grant FT/STX transfer rights, the trait contract executes with the swap contract as tx-sender, potentially enabling indirect operations.

Impact: The deployer is the sole gatekeeper — only tx-sender == deployer can call this function. If the deployer's keys are compromised, an attacker could pass a malicious contract that drains funds. Even without key compromise, this is a trust assumption: users must trust the deployer will only enroll legitimate contracts.

Recommendation: Consider whitelisting specific enroll contracts rather than accepting arbitrary traits. A mapping of approved contracts or a registry check would reduce the blast radius of a key compromise:

(define-map approved-enroll-contracts principal bool)
(asserts! (default-to false (map-get? approved-enroll-contracts (contract-of enroll-contract))) err-forbidden)
MEDIUM

M-01: init-unwrap sweeps entire xBTC balance, including new deposits

Location: init-unwrap

Description: The operator sweeps the entire xBTC balance to the custodian:

(let (
    (balance (get-xbtc-balance current-contract))
    ...
  )
  (try! (as-contract? (...) (try! (contract-call? ... transfer balance current-contract xbtc-receiver none))))
)

There is a race condition: if a user calls deposit-xbtc in the same block as (or just before) init-unwrap, their deposit is swept immediately — even though they may have intended to withdraw their xBTC before the next cycle. After the sweep, withdraw-xbtc will fail because the contract holds no xBTC.

Impact: Users who deposit shortly before a sweep lose the ability to withdraw xBTC. They must wait for the custodian to complete the full BTC → sBTC bridge cycle (potentially 2+ weeks) before they can claim sBTC. The user doesn't lose funds, but their liquidity is locked for an indeterminate period.

Recommendation: Consider a snapshot mechanism: only sweep deposits that existed at a cutoff point (e.g., end of previous cycle). Alternatively, emit a warning event before sweeps or add a time-lock between deposit and sweep eligibility.

MEDIUM

M-02: No mechanism to update custodian or operator after initialization

Location: initialize

Description: The initialize function can only be called once — it asserts both custodian and custodian-operator are none:

(asserts! (is-none (var-get custodian)) err-forbidden)
(asserts! (is-none (var-get custodian-operator)) err-forbidden)

There is no function to rotate the custodian or operator. If the custodian's keys are lost or compromised, the contract cannot be pointed to a new custodian. The xBTC sweep process would be permanently broken.

Impact: Key loss or compromise of the custodian address permanently disables the swap pipeline. Deposited xBTC and unclaimed sBTC would be locked. Since the deployer can't update these addresses, a new v5 contract would need to be deployed, and users would need to migrate.

Recommendation: Add deployer-gated functions to rotate the custodian and operator:

(define-public (set-custodian (new-custodian principal))
  (begin
    (asserts! (is-eq tx-sender deployer) err-unauthorized)
    (var-set custodian (some new-custodian))
    (ok true)
  )
)
LOW

L-01: claim-sbtc partial claim silently reduces amount without notification

Location: claim-sbtc

Description: The claim function uses a min(balance, sbtc-balance) pattern:

(amount (if (< balance sbtc-balance)
  balance
  sbtc-balance
))

If the contract holds less sBTC than the user's IOU balance, the user receives a partial claim. The remaining IOUs stay intact for future claims. This is a reasonable design for gradual sBTC availability, but the user receives no on-chain indication that the claim was partial.

Impact: Users may not realize they received less than their full entitlement. No event distinguishes a full claim from a partial one. UIs would need to compare the user's IOU balance before and after to detect partial fills.

Recommendation: Add a print event that includes both the requested amount (full IOU balance) and the actual amount claimed, allowing off-chain systems to detect and display partial claims:

(print {event: "claim-sbtc", user: user, requested: balance, claimed: amount, remaining: (- balance amount)})
INFO

I-01: Clarity 4 as-contract? usage — well-scoped token allowances

Location: withdraw-xbtc, init-unwrap, transfer-sbtc-to

Description: The contract correctly uses Clarity 4's as-contract? with explicit with-ft allowances. For example, withdraw-xbtc grants exactly the amount being transferred:

(as-contract?
  ((with-ft 'SP3DX3H4FEYZJZ586MFBS25ZW3HZDMEW92260R2PR.Wrapped-Bitcoin
    "wrapped-bitcoin" amount))
  (begin
    (try! (contract-call? .swapping-xbtc-v4 burn amount user))
    (try! (contract-call? ... transfer amount current-contract user none))
  )
)

This is the correct pattern — the callee can only transfer exactly amount of the specified FT, preventing over-withdrawal even if the inner call logic is flawed.

Impact: Positive. This contract demonstrates proper Clarity 4 security hygiene. The with-ft scoping eliminates the blanket-authority risk that affects pre-Clarity 4 as-contract contracts.

Recommendation: No change needed. This is exemplary usage of Clarity 4's scoped authority model.

INFO

I-02: Top-level set-swap-contract call executes at deploy time

Location: Last line of contract

Description: The contract ends with a top-level expression:

(try! (contract-call? .swapping-xbtc-v4 set-swap-contract current-contract))

This executes during contract deployment, registering this contract as the authorized swap contract in the swapping-xbtc-v4 IOU token. This is a common Clarity pattern for atomic initialization — the IOU token will only accept mint/burn calls from this contract.

Impact: Positive. The deploy-time registration ensures the IOU token is locked to this specific swap contract from the moment of deployment, with no window for a race condition.

Recommendation: No change needed. This is a well-known and safe Clarity deployment pattern.

Positive Observations

  • Clarity 4 best practices: All as-contract? calls use explicit with-ft scoping for token transfers, limiting authority to exactly the required amount and token — a model implementation
  • Graceful partial claims: claim-sbtc uses min(balance, available) rather than reverting, allowing users to claim whatever sBTC is available without waiting for full liquidity
  • Excess recovery: withdraw-excess-sbtc is permissionless and routes surplus sBTC (above IOU supply) to the swap wallet, preventing tokens from being stranded in the contract
  • One-time initialization: initialize can only be called once and only by the deployer, preventing re-initialization attacks
  • Atomic IOU binding: Deploy-time set-swap-contract call ensures the IOU token is permanently bound to this contract
  • Clean separation of roles: Deployer (admin), operator (triggers sweeps), custodian (receives xBTC) — three distinct roles with minimal overlap

Trust Assumptions

This contract operates a semi-custodial model. Users must trust:

  • The custodian will actually bridge xBTC → BTC → sBTC and not abscond with the xBTC
  • The operator will trigger init-unwrap at reasonable intervals
  • The deployer will not enroll the contract in malicious trait contracts via enroll
  • The sBTC bridge will function correctly and deliver sBTC to this contract's address

These trust assumptions are inherent to the xBTC → sBTC migration problem — there is no trustless way to atomic-swap between xBTC (a wrapped SIP-010) and sBTC (a bridge-minted asset) without an intermediary step through BTC L1.
