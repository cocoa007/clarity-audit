Overview

This contract tracks sBTC reward positions for StackingDAO's stSTXbtc token holders. sBTC rewards are distributed proportionally to holders based on their tracked positions. Wallet positions are tracked automatically; positions in external protocols (DEXes, lending, etc.) require manual refresh via refresh-position with a position trait.

The architecture follows a data/logic separation: ststxbtc-tracking-v2 contains business logic (reward calculation, position tracking, claims), while ststxbtc-tracking-data-v2 is a pure data store with DAO-gated setters. A cumulative reward per token model distributes sBTC proportionally.

Audit confidence: Medium. Multi-contract system with external dependencies on .dao, position traits, and .sbtc-token. Core reward math is straightforward. The total-supply is managed externally, which introduces trust assumptions not visible in this contract alone.

Documented Limitations

  • TODO: update with mainnet sbtc token — the sBTC token reference is a placeholder
  • Positions in other protocols need manual refresh via refresh-position
  • All privileged operations gated by .dao check-is-protocol

Findings

HIGH H-01: Division by Zero in add-rewards When Total Supply is Zero

Location: ststxbtc-tracking-v2 — add-rewards

Description: The function divides by get-total-supply to calculate per-token rewards. If total supply is zero (before any positions are tracked, or after a migration reset), Clarity's division by zero causes a runtime abort, reverting the entire transaction including the sBTC transfer.

(define-public (add-rewards (amount uint))
  (let (
    (reward-added-per-token (/ (* amount u10000000000)
      (contract-call? .ststxbtc-tracking-data-v2 get-total-supply)))
    ;; Division by zero here if total-supply == 0
    ...

Impact: Rewards cannot be distributed when no positions are tracked. In a migration scenario where positions haven't been re-registered yet, incoming sBTC rewards would fail to be accepted, requiring manual retry. Since sBTC transfers revert with the tx, no funds are lost — but the operational disruption could cause reward delays.

Recommendation: Guard against zero total supply:

(asserts! (> (contract-call? .ststxbtc-tracking-data-v2 get-total-supply) u0)
  (err ERR_NO_SUPPLY))

MEDIUM M-01: Permissionless claim-pending-rewards Allows Forced Claims for Any Holder

Location: ststxbtc-tracking-v2 — claim-pending-rewards, claim-pending-rewards-many

Description: Anyone can call claim-pending-rewards for any (holder, position) pair. The sBTC is sent to holder, not the caller, so no theft is possible. However, this enables griefing:

  • Forcing unwanted token receipts on contracts that may not handle sBTC
  • Triggering taxable events for holders who prefer to defer claims
  • The batch variant claim-pending-rewards-many amplifies this to 200 holders per call
(define-public (claim-pending-rewards (holder principal) (position principal))
  (let (
    (pending-rewards (unwrap-panic (get-pending-rewards holder position)))
  )
    ;; No check: tx-sender == holder
    (asserts! (var-get claims-enabled) (err ERR_CLAIMS_DISABLED))
    (if (>= pending-rewards u1)
      (begin
        (try! (as-contract (contract-call? .sbtc-token transfer
          pending-rewards tx-sender holder none)))
        ...

Impact: Holders cannot control the timing of their own claims. An attacker could force-claim for all tracked holders in a single transaction.

Recommendation: Add caller verification: (asserts! (is-eq tx-sender holder) (err ERR_NOT_AUTHORIZED)), or require DAO protocol authorization for batch claims.

MEDIUM M-02: Permissionless save-pending-rewards Enables External Checkpoint Manipulation

Location: ststxbtc-tracking-v2 — save-pending-rewards

Description: The function is public with no access control. Anyone can call it to snapshot a holder's pending rewards and update their cumulative reward checkpoint. While saved rewards are preserved (not lost), this allows an external party to manipulate when checkpoints occur.

(define-public (save-pending-rewards (holder principal) (position principal))
  (let (
    (pending-rewards (unwrap-panic (get-pending-rewards holder position)))
    (existing-rewards (get-saved-rewards holder position))
  )
    ;; No access control check
    (if (> (- pending-rewards existing-rewards) u0)
      (begin
        (map-set saved-rewards { holder: holder, position: position } pending-rewards)
        (try! (contract-call? .ststxbtc-tracking-data-v2 update-holder-position holder position))
        ...

Impact: Combined with M-01, an attacker has full external control over a holder's reward lifecycle — checkpoint, then claim. Saved rewards aren't lost, so the direct financial impact is low, but this breaks the expectation that holders manage their own state.

Recommendation: Restrict to DAO protocol callers or require tx-sender == holder.

LOW L-01: Precision Loss in Reward Distribution

Location: ststxbtc-tracking-v2 — add-rewards

Description: The reward-per-token calculation uses integer division: (/ (* amount 1e10) total-supply). For small reward amounts relative to large total supply, the quotient truncates to zero, and those rewards are permanently locked in the contract.

Example: If amount = 1 (1 sat) and total-supply = 20000000000 (200 sBTC), then reward-added-per-token = 10000000000 / 20000000000 = 0. The 1 sat is transferred in but never distributable.

Impact: Dust amounts of sBTC become permanently locked. Negligible for normal operation but accumulates over time.

Recommendation: Track a dust remainder variable and carry it forward to the next distribution.

LOW L-02: unwrap-panic Used Where try! Would Be Safer

Location: claim-pending-rewards, save-pending-rewards

Description: Both functions use (unwrap-panic (get-pending-rewards ...)). Currently get-pending-rewards always returns (ok ...), making this safe. However, if the read-only function is ever modified to return errors, these calls would become unrecoverable transaction aborts.

Impact: Defensive coding concern — no current risk.

Recommendation: Replace with (try! (get-pending-rewards ...)) for graceful error propagation.

INFO I-01: Pre-Clarity 4 as-contract Without Asset Restrictions

Location: claim-pending-rewards, withdraw-tokens, add-rewards

Description: Uses legacy as-contract which grants blanket authority over all contract assets. Clarity 4 introduced as-contract? with explicit asset allowances, which would restrict the contract to only moving sBTC when intended.

Recommendation: Migrate to Clarity 4:

(as-contract?
  (contract-call? .sbtc-token transfer pending-rewards tx-sender holder none)
  (with-ft .sbtc-token pending-rewards)
)

INFO I-02: total-supply Managed Externally — Not Synchronized by Tracking Contract

Location: ststxbtc-tracking-data-v2 — total-supply variable

Description: The tracking contract never calls set-total-supply. This value must be maintained by an external protocol contract. If it falls out of sync with actual tracked positions, reward calculations become incorrect — over-distributing (supply too low) or under-distributing (supply too high).

Impact: Correctness of the entire reward system depends on an external contract keeping total-supply accurate. This is a trust assumption not visible from this contract alone.

Recommendation: Document the dependency clearly. Consider having refresh-wallet and refresh-position atomically update total-supply as positions change.

Architecture Notes

  • Reward model: Cumulative reward per token (scaled by 1e10). When rewards are added, cumm-reward increases. Each holder's pending rewards = (current_cumm - holder_cumm) × amount / 1e10 + saved_rewards.
  • Position types: Wallet positions (holder == position) are refreshed via refresh-wallet. External positions (DEX LP, lending, etc.) implement position-trait and are refreshed via refresh-position.
  • Reserve mechanism: Each supported position has a reserve principal and a cap. refresh-position enforces ERR_OVER_RESERVE — positions cannot exceed their reserve allocation.
  • Deactivation: When a position is deactivated, its deactivated-cumm-reward is frozen. Future reward calculations for that position use the frozen value instead of the live cumm-reward, ensuring holders don't earn rewards after deactivation.
  • Data separation: All state is in ststxbtc-tracking-data-v2 with DAO-gated setters, enabling logic upgrades without data migration.
