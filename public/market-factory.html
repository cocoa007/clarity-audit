Market Factory v18-bias — Audit

SP3N5CN0PE7YRRP29X7K9XG22BT861BRS5BN8HFFA.market-factory-v18-bias
Audited: February 20, 2026 · By: cocoa007

Overview

A binary prediction market contract using the Logarithmic Market Scoring Rule (LMSR) with a bias mechanism for setting initial probabilities via virtual liquidity. Deployed on Stacks mainnet.

Key properties:

  • Binary YES/NO outcomes, admin-resolved
  • LMSR pricing with fixed liquidity parameter b
  • Bias mechanism: virtual shares (rY, rN) shift initial pricing without affecting redemption
  • Dual-unit system: STX integers for math, uSTX for transfers
  • Full exp, ln Taylor series implementation in Clarity
  • Closed-form buy inversion (no binary search)
Findings Summary
  • CRITICAL ~46% of sell positions revert due to integer truncation
  • MEDIUM bump-cap-if-needed lets users bypass spending caps
  • MEDIUM No cap on combined fee rate (protocol + LP can exceed 100%)
  • MEDIUM 1 STX minimum cost floor causes ~2x overpay on small trades
  • LOW ln-atanh accuracy degrades at extreme values
  • LOW Single admin key, no multisig or timelock
  • LOW No share transfers (positions are non-composable)
  • INFO withdraw-surplus blocks if winners never redeem
  • INFO Market IDs are caller-supplied (no auto-increment)
  • INFO exp-taylor 6-term accuracy: ~13 ppm error at boundary

Architecture

The contract is a factory — one deployment serves unlimited markets, indexed by m: uint. All state lives in maps with composite keys.

;; Per-market state (maps keyed by { m: uint })
m-status, m-outcome, m-initialized, m-paused, m-max-trade
m-q-yes, m-q-no   ;; real share quantities (STX-scale)
m-pool             ;; liquidity pool (uSTX)
m-b                ;; LMSR liquidity parameter (STX-scale)
m-r-yes, m-r-no    ;; bias virtual shares (STX-scale)

;; Per-user-per-market (maps keyed by { m: uint, user: principal })
yes-holdings, no-holdings  ;; share balances
user-caps, user-spent      ;; spending limits

Findings

F-01: ~46% of sell positions permanently revert

Location: do-sell → cost-tilde difference calculation

Description: The LMSR cost function operates in STX integers. When selling 1 share, the contract computes cost_tilde(qY) - cost_tilde(qY-1). Because both sides are truncated integers, this difference is often 0 even when the real LMSR says the share is worth ~0.5 STX.

The contract then hits asserts! (> diff 0) ERR-BAD-REFUND and reverts.

Numerical proof (b=144, ~100 STX market):

Stuck positions (sell 1 share reverts):
  qY=2:  cost_tilde(2)=1, cost_tilde(1)=1, diff=0  ← REVERTS
  qY=4:  cost_tilde(4)=2, cost_tilde(3)=2, diff=0  ← REVERTS
  qY=6:  cost_tilde(6)=3, cost_tilde(5)=3, diff=0  ← REVERTS
  qY=8:  cost_tilde(8)=4, cost_tilde(7)=4, diff=0  ← REVERTS
  qY=10: cost_tilde(10)=5, cost_tilde(9)=5, diff=0 ← REVERTS
  ... (23 out of 50 positions affected)

Workaround: sell 2+ shares at once (diff becomes ≥ 1).
But if you hold exactly 1 share at a stuck position → cannot sell.

Impact: Users who hold 1 share at certain market states cannot exit their position. They must either buy more shares first (costing additional STX) or wait for resolution.

Root cause: LMSR math in STX integers is too coarse. Each share costs ~0.5 STX, but the integer representation can't distinguish cost_tilde(N) from cost_tilde(N-1) when both round to the same integer.

Fix: Run LMSR math in uSTX (multiply all quantities by UNIT) or use the 1e6 fixed-point scale for cost calculations before converting to transfer amounts.

F-02: Self-service cap bypass via buy-*-auto

Location: buy-yes-auto, buy-no-auto

(define-public (buy-yes-auto (m uint) (amount uint) (target-cap uint) (max-cost uint))
  (begin
    ...
    (bump-cap-if-needed m tx-sender target-cap)  ;; ← user controls target-cap
    ...))

The target-cap parameter is user-supplied. bump-cap-if-needed will increase the user's spending cap to any value they pass. This makes the cap system entirely self-service — the user-caps map becomes meaningless as a risk control.

The non-auto buy-yes/buy-no enforces the existing cap but requires admin to have set it first (and defaults to 0, blocking the buy).

Impact: Any spending limits set by admin can be bypassed by calling the auto variant.

Fix: Remove bump-cap-if-needed from buy functions, or require admin signature for cap changes.

F-03: Combined fees can exceed 100%

Location: set-fees

(asserts! (<= protocol-bps u10000) (err u740))
(asserts! (<= lp-bps       u10000) (err u741))
;; Missing: (asserts! (<= (+ protocol-bps lp-bps) u10000) ...)

Each fee is independently capped at 100%, but there's no combined cap. Admin could set protocol=5000 bps + LP=5000 bps = 100% total fees, meaning users pay 2x the base cost. The fees-locked one-way lock mitigates this after locking.

Fix: Add (asserts! (<= (+ protocol-bps lp-bps) u10000) (err u744))

F-04: 1 STX minimum cost floor causes ~2x overpay

Location: calculate-cost

(if (> diff 0)
    (let ((u (to-uint diff))) (if (> u u0) u u1))
    u1)  ;; minimum cost: 1 STX per trade

For a 50/50 market, 1 share theoretically costs ~0.5 STX via LMSR. But the integer floor + minimum forces 1 STX. Users overpay by ~0.5 STX on every single-share purchase. This holds for all market sizes:

Market SizebReal Cost (1 share)ChargedOverpay
10 STX140.509 STX1 STX491,073 uSTX
100 STX1440.501 STX1 STX499,132 uSTX
1000 STX14420.500 STX1 STX499,913 uSTX

Note: This actually helps solvency — the pool overcollects. But it's user-hostile pricing for small positions.

F-05: ln-atanh accuracy degrades at extreme inputs

Location: ln-atanh, ln-general

The ln(y) implementation uses 2 * atanh((y-1)/(y+1)) with a 5th-order series (up to t⁹). Convergence requires t to be small, which means y should be near 1.0. The ln-general normalizer does 8 halving/doubling steps, covering a range of ~2⁸ = 256x. For markets with extreme imbalances (e.g., qY >> qN with large b), the inputs to ln-sum-exp could push beyond this range.

Impact: Mispricing on extreme-probability markets. Unlikely in practice with reasonable b values.

F-06: Single admin, no multisig or timelock

Location: ADMIN constant

One hardcoded principal controls: market creation, resolution, pausing, fee configuration, surplus withdrawal. No oracle, no dispute mechanism, no timelock. Compromised admin key = incorrect resolutions + pool drainage.

F-07: No share transfers

YES/NO holdings are maps with no transfer function. Positions are non-transferable — no secondary market, no composability, no recovery from lost keys.

F-08: withdraw-surplus deadlocks if winners don't redeem

Location: withdraw-surplus

(if (is-eq out "YES")
    (asserts! (is-eq ys u0) (err u708))   ;; ALL yes shares must be redeemed
    (asserts! (is-eq ns u0) (err u709)))

Admin can only withdraw surplus after every winning share is redeemed. If any winner loses their key or abandons dust, the surplus is permanently locked. No expiry or sweep mechanism.

F-09: No market ID auto-increment

create-market (m uint) ... — the ID is caller-supplied. Duplicate check exists (get-initialized-bool), but admin must track IDs externally. Minor operational risk.

F-10: Taylor series precision at boundary

The 6-term exp-taylor has ~13 ppm error at |r| ≈ ln(2) ≈ 0.693. For a 10,000 STX pool, that's ~0.13 STX per trade. Compounds over many trades but within acceptable bounds for prediction market pricing.

What's Done Well

Solvency guard per trade

Every buy checks pool + baseUstx >= max(yesSupply, noSupply) * UNIT after the trade. This catches integer rounding issues before they become critical. Smart defensive coding.

Bias separation

Virtual liquidity (rY, rN) only enters the pricing function, never the redemption logic. Winners always get exactly balance * UNIT uSTX regardless of bias. Clean separation of pricing concerns from settlement.

Closed-form cost inversion

Instead of binary search to answer "how many shares for X budget?", the contract derives it analytically: x = b * ln(E(1+D) - D) with a 2-step refinement. Much more gas-efficient than iteration.

One-way fee lock

lock-fees-config is irreversible — once locked, fee parameters can never change. Simple trust primitive that works.

Sell fee clamping

minu(feeP, baseUstx) ensures fees never exceed proceeds on sells. Prevents negative payouts from fee rounding.

Methodology

Full source read from Hiro API (/v2/contracts/source/...). Unit tracing through every code path. Numerical simulation of LMSR cost function in Python with exact floating-point comparison against the integer math the contract uses. No formal verification — findings are from manual analysis.
