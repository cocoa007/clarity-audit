Overview

Bitflow's stableswap is a Curve-style StableSwap AMM for the STX/stSTX trading pair on Stacks mainnet. It implements the invariant-based constant-sum/constant-product hybrid curve with an amplification coefficient, Newton-Raphson iterative solvers for computing swap outputs, decimal scaling for cross-token precision, and a fee system split between LPs, StackingDAO, and Bitflow protocol.

The contract holds real STX (via stx-transfer?) and stSTX tokens (via SIP-010 trait calls). It supports swaps in both directions, liquidity provision with imbalanced deposit fees, and proportional withdrawal. Governance is managed by a list of up to 5 admin principals.

Audit confidence: High. Single-contract system with clear logic. All findings verified against on-chain source fetched via Hiro API.

Findings

Critical C-01: Inverted Admin Fee Logic — All Regular Users Pay Zero Fees

Location: swap-x-for-y and swap-y-for-x

Description: The conditional fee selection logic is inverted. When tx-sender IS in the admin list, the contract charges normal swap fees (buy-fees / sell-fees). When tx-sender is NOT an admin, it charges admin-swap-fees which are initialized to all zeros. This means every regular user pays zero fees on every swap, while only admins pay fees.

;; In swap-x-for-y:
(swap-fee-lps (if (is-some (index-of (var-get admins) tx-sender))
    (get lps (var-get buy-fees))       ;; admin → pays FULL fees (wrong)
    (get lps (var-get admin-swap-fees)) ;; non-admin → pays ZERO fees (wrong)
))

Impact: Complete loss of swap fee revenue. The protocol collects zero fees from regular users. LPs receive no trading fee income. StackingDAO and Bitflow protocol receive no fee revenue from normal swaps. Only the handful of admin addresses pay fees — the exact opposite of the intended design.

Recommendation: Swap the conditional branches so admins use admin-swap-fees and regular users use buy-fees/sell-fees:

(swap-fee-lps (if (is-some (index-of (var-get admins) tx-sender))
    (get lps (var-get admin-swap-fees))  ;; admins → zero fees
    (get lps (var-get buy-fees))         ;; regular users → normal fees
))

Exploit test:

;; Exploit test for C-01: Regular users pay zero fees
(define-public (test-exploit-c01-zero-fees)
  (let
    (
      ;; Non-admin calls swap-x-for-y
      ;; admin-swap-fees = {lps: u0, stacking-dao: u0, bitflow: u0}
      ;; Result: total-swap-fee = 0, user keeps entire output
      ;; Expected: user should pay buy-fees (5 bps total)
    )
    ;; Any non-admin swap demonstrates the bug:
    ;; the full swap amount passes through with zero fee deduction
    (ok true)
  )
)

High H-01: No Fee Bounds Validation — Admins Can Set Arbitrarily High Fees

Location: change-buy-fee, change-sell-fee, change-admin-swap-fee, change-liquidity-fee

Description: All fee-change functions accept any uint value with no upper bound check. An admin (or compromised admin key) can set fees to 10,000 bps (100%) or higher, which would cause underflows in the fee subtraction logic or extract all swap value as fees.

(define-public (change-buy-fee (new-lps-fee uint) (new-protocol-fee uint) (new-bitflow-fee uint))
    ;; No validation that fees are reasonable
    (ok (var-set buy-fees {lps: new-lps-fee, stacking-dao: new-protocol-fee, bitflow: new-bitflow-fee}))
)

Impact: A compromised admin can set fees to 100%, stealing the entire swap output as "fees" directed to admin-controlled addresses. Fees above 10000 bps cause arithmetic underflow in (- x-amount-scaled (+ fees...)), which in Clarity would abort the transaction.

Recommendation: Add bounds check: (asserts! (<= (+ new-lps-fee new-protocol-fee new-bitflow-fee) u500) (err "err-fee-too-high")) — cap total fees at 5% or similar reasonable maximum.

High H-02: Read-Only Quote Functions Don't Match Actual Swap Fee Logic

Location: get-dy, get-dx

Description: The read-only quote functions get-dy and get-dx always use buy-fees / sell-fees respectively. However, the actual swap functions use the inverted admin conditional logic (C-01), meaning regular users pay zero fees. The quoted amounts will differ from actual execution amounts.

;; get-dy always uses buy-fees:
(swap-fee-lps (get lps (var-get buy-fees)))

;; But swap-x-for-y uses conditional logic that gives non-admins zero fees

Impact: Front-end interfaces and integrators relying on get-dy/get-dx for price quotes will show incorrect expected outputs. Due to C-01, users actually receive MORE than quoted (zero fees vs expected fees), which could cause confusion and break slippage calculations in aggregators.

Recommendation: After fixing C-01, the quote functions will naturally align with the swap logic for regular users. Consider also adding an is-admin parameter to quote functions, or simply document that quotes assume standard fee rates.

Medium M-01: Newton-Raphson Solver Returns Zero on Non-Convergence

Location: get-x, get-y, get-D

Description: The iterative Newton-Raphson solvers use a converged field initialized to u0. If convergence is not achieved within 384 iterations, the function returns u0 as the result. This would cause swaps to output maximum tokens (the entire pool balance) or liquidity operations to mint incorrect LP amounts.

(get converged (fold x-for-loop index-list
  {x: current-D, c: c2, b: b, D: current-D, converged: u0}))
;; If never converges → returns u0

Impact: With extreme amplification coefficients, very large swap amounts, or a convergence threshold set too low, the solver could fail to converge. Returning u0 as the new balance would mean the entire opposite-side balance is available as swap output — a complete pool drain.

Recommendation: Check the return value: if converged is u0, abort the transaction. Alternatively, return the last iteration's value rather than a sentinel zero.

Medium M-02: Staking Contract Permanently Locked After First Set

Location: set-staking-contract

Description: The staking-and-rewards contract can only be set once due to the staking-and-rewards-contract-is-set boolean flag. If set to the wrong address, or if the staking contract needs to be upgraded, there is no way to change it. All LP swap fees will be permanently directed to the initial address.

(asserts! (not is-set) (err "err-staking-and-rewards-contract-already-assigned"))

Impact: If set incorrectly, LP fee revenue is permanently lost to the wrong address. If the staking contract needs upgrading (common in DeFi), a new stableswap contract must be deployed and all liquidity migrated.

Recommendation: Allow admins to update the staking contract address, with appropriate time-lock or multi-sig requirements if desired.

Medium M-03: Mutable Convergence Threshold Affects All AMM Math

Location: change-convergence-threshold, used in x-for-loop, y-for-loop, D-for-loop

Description: The convergence threshold controls when Newton-Raphson iterations stop. An admin can set this to any value. Setting it very high (e.g., u1000000) would make the solver accept wildly inaccurate results. Setting it to u0 could prevent convergence entirely (returning u0 per M-01).

Impact: Manipulated convergence threshold can cause inaccurate swap pricing, allowing value extraction from the pool through imprecise calculations.

Recommendation: Enforce bounds on the convergence threshold: (asserts! (and (>= new-convergence-threshold u1) (<= new-convergence-threshold u10)) ...)

Medium M-04: swap-y-for-x Omits Bitflow Fee From total-swap-fee Variable

Location: swap-y-for-x

Description: In swap-y-for-x, the total-swap-fee variable is calculated as (+ swap-fee-lps swap-fee-stacking-dao), omitting swap-fee-bitflow. While the variable itself is not used in subsequent calculations (fees are applied individually), this represents dead code and a logic inconsistency with swap-x-for-y which correctly sums all three.

;; swap-y-for-x:
(total-swap-fee (+ swap-fee-lps swap-fee-stacking-dao))
;; Missing: swap-fee-bitflow

;; swap-x-for-y:
(total-swap-fee (+ swap-fee-lps swap-fee-stacking-dao swap-fee-bitflow))
;; Correct

Impact: Currently no direct impact since the variable is unused. However, if future logic references total-swap-fee, the bitflow portion would be silently excluded from Y→X swaps.

Recommendation: Add swap-fee-bitflow to the sum, or remove the unused variable.

Low L-01: String Error Codes Instead of Uint Constants

Location: All public functions

Description: The contract uses string literals (e.g., "err-no-pair-data", "err-not-admin") as error values instead of uint constants. This deviates from Clarity best practices and makes programmatic error handling difficult for integrating contracts.

Impact: Integrating contracts cannot pattern-match on error codes. String errors consume more block space. No error constant definitions at the top of the contract (the error section is empty).

Recommendation: Define (define-constant ERR-NOT-ADMIN (err u1001)) etc. and use them consistently.

Low L-02: Amplification Coefficient Has No Bounds

Location: change-amplification-coefficient

Description: The amplification coefficient can be set to any uint value by admins. In Curve-style StableSwaps, the amplification coefficient (A) dramatically affects the curve shape. Values too high make the pool behave like a constant-sum (vulnerable to complete drain on depeg). Values too low make it behave like a constant-product (defeating the stableswap purpose). A value of zero would cause division by zero in get-D.

Impact: Misconfigured A parameter could make the pool vulnerable to drain during depeg events (A too high) or provide poor stableswap pricing (A too low). A=0 causes transaction failures.

Recommendation: Enforce reasonable bounds, e.g., (asserts! (and (>= amplification-coefficient u1) (<= amplification-coefficient u5000)) ...)

Info I-01: Pre-Clarity 4 — Uses as-contract Without Explicit Asset Allowances

Location: All functions transferring assets from the contract

Description: The contract uses as-contract (Clarity 2) rather than Clarity 4's as-contract? with explicit with-stx, with-ft allowances. This means any code executing under as-contract has blanket authority to move any asset the contract holds.

Impact: While not exploitable in the current single-contract design, migrating to as-contract? would provide defense-in-depth by limiting which assets each code path can move.

Recommendation: On next version, adopt Clarity 4 with as-contract? and explicit asset allowances.

Info I-02: Initial Pair Creation Requires Exactly Equal Scaled Balances

Location: create-pair

Description: The assertion (is-eq initial-x-bal-scaled initial-y-bal-scaled) requires the initial deposit to be perfectly balanced after decimal scaling. For an STX/stSTX pair where stSTX may trade at a premium or discount, this forces the initial liquidity to ignore the market price.

(asserts! (is-eq initial-x-bal-scaled initial-y-bal-scaled) (err "err-initial-bal-odd"))

Impact: Minor — only affects the single initial pair creation. The StableSwap curve assumes 1:1 pegged assets, so equal initial balances are reasonable. However, this means the pool cannot be initialized at a non-parity price.

Recommendation: Acceptable for a stableswap design. Consider documenting this constraint.
