Overview

Freddie is the core vault manager for the Arkadiko stablecoin protocol on Stacks. It orchestrates collateralized debt positions (CDPs) that back the USDA stablecoin. Users deposit STX or SIP-010 tokens as collateral and mint USDA against it, similar to MakerDAO's CDP system.

The contract manages the full vault lifecycle: creation, deposits, withdrawals, minting, burning, stacking integration, stability fees, liquidation, and auction settlement. It delegates custody to separate reserve contracts and validates all trait parameters against a DAO registry — a well-architected separation of concerns.

Architecture

  • Vault data stored in arkadiko-vault-data-v1-1 (separate storage contract)
  • Collateral custody in arkadiko-stx-reserve-v1-1 / arkadiko-sip10-reserve-v1-1
  • Price feeds via arkadiko-oracle-trait-v1 implementations
  • Liquidations triggered by arkadiko-liquidator, settled by arkadiko-auction-engine
  • PoX stacking integration for STX collateral via stacker contracts

Documented Limitations

  • Contract is v1-1, superseded by later versions in the Arkadiko protocol
  • Limited to 4 stacker contracts (stacker through stacker-4)
  • Stability fees use simple (linear) interest model

Findings

HIGH

H-01: Missing Owner Check in close-vault Allows Forced Vault Closure

Location: close-vault function

Description: The close-vault function does not verify that tx-sender is the vault owner. Any user can call close-vault on another user's vault, provided the vault has no stacked tokens and is not liquidated. The function burns USDA from the vault owner and returns collateral to the vault owner — so the attacker doesn't steal funds, but they force an unwanted position closure.

(define-public (close-vault
  (vault-id uint)
  (reserve <vault-trait>)
  (ft <ft-trait>)
  (coll-type <collateral-types-trait>)
)
  (let ((vault (get-vault-by-id vault-id))
       (updated-vault ...))
    (asserts! (is-eq u0 (get stacked-tokens vault)) (err ERR-STACKING-IN-PROGRESS))
    ;; ... no (asserts! (is-eq tx-sender (get owner vault))) check ...
    (if (is-eq (get debt vault) u0)
      true
      (try! (contract-call? .arkadiko-dao burn-token .usda-token (get debt vault) (get owner vault)))
    )
    (try! (contract-call? reserve burn ft (get owner vault) (get collateral vault)))
    ...

Impact: An attacker can force-close any non-stacking vault. If the vault owner currently holds enough USDA, their debt is burned and collateral returned — but this disrupts their position. If the owner doesn't hold enough USDA, the call reverts (no loss, but griefing potential). This is particularly harmful when a user intentionally maintains a leveraged position and the attacker forces closure during unfavorable market conditions.

Recommendation: Add owner verification:

(asserts! (is-eq tx-sender (get owner vault)) (err ERR-NOT-AUTHORIZED))
HIGH

H-02: Stability Fee Overwrite in mint — Accrued Fees Erased

Location: mint function

Description: The mint function reads the vault state into vault at the beginning of execution, computes updated-vault from this snapshot, then calls accrue-stability-fee which updates the vault in storage with new stability-fee-accrued and stability-fee-last-accrued values. Finally, update-vault is called with updated-vault — which was derived from the stale pre-accrual state — overwriting the accrued fees.

(define-public (mint ...)
  (let (
    (vault (get-vault-by-id vault-id))         ;; snapshot BEFORE accrual
    (updated-vault (merge vault {              ;; computed from stale snapshot
      debt: new-total-debt,
      updated-at-block-height: block-height
    }))
    ...
  )
    ...
    (try! (accrue-stability-fee vault-id coll-type))   ;; updates vault in storage
    ...
    (try! (contract-call? .arkadiko-vault-data-v1-1
      update-vault vault-id updated-vault))            ;; OVERWRITES with stale data
    ...

Impact: Every call to mint resets the vault's stability-fee-accrued to its pre-accrual value and resets stability-fee-last-accrued to the old block height. This effectively erases all stability fees accrued up to that point. A sophisticated user could call mint with minimal extra debt periodically to continuously reset their fee obligation to near zero, resulting in protocol revenue loss.

Recommendation: Re-read the vault state after accrue-stability-fee and compute updated-vault from the fresh state:

;; After accruing fees, re-read the vault
(try! (accrue-stability-fee vault-id coll-type))
(let ((fresh-vault (get-vault-by-id vault-id)))
  (try! (contract-call? .arkadiko-vault-data-v1-1
    update-vault vault-id (merge fresh-vault {
      debt: new-total-debt,
      updated-at-block-height: block-height
    })))
)
MEDIUM

M-01: Permissionless redeem-tokens — Anyone Can Trigger Fee Distribution

Location: redeem-tokens function

Description: The redeem-tokens function has no caller authorization check. It only verifies that 31 days have passed since the last payout. Any user can trigger the transfer of USDA and DIKO from the Freddie contract to the DAO payout address.

(define-public (redeem-tokens (usda-amount uint) (diko-amount uint))
  (begin
    (asserts! (> (- block-height (var-get block-height-last-paid)) (* BLOCKS-PER-DAY u31))
      (err ERR-NOT-AUTHORIZED))
    ;; No caller check — anyone can call this
    (var-set block-height-last-paid block-height)
    ...

Impact: While funds are sent to the legitimate payout address (not the caller), anyone can force the timing of payouts. An attacker could trigger a payout immediately after the 31-day window opens with arbitrary amounts (up to contract balance), potentially disrupting treasury management. The caller also specifies the amounts, so they could trigger a payout of just 1 uUSDA to reset the 31-day timer and grief future legitimate payouts.

Recommendation: Add DAO owner or guardian authorization check.

MEDIUM

M-02: release-stacked-stx Missing Access Control

Location: release-stacked-stx function

Description: The release-stacked-stx function has no caller restriction. Anyone can call it for any liquidated xSTX vault once the stacking unlock height is reached. The function adds the stacked amount to stx-redeemable and zeros out stacked-tokens.

(define-public (release-stacked-stx (vault-id uint))
  (let ((vault (get-vault-by-id vault-id)))
    ;; No caller check
    (asserts! (is-eq "xSTX" (get collateral-token vault)) ...)
    (asserts! (is-eq true (get is-liquidated vault)) ...)
    (asserts! (> (get stacked-tokens vault) u0) ...)
    (asserts! (>= burn-block-height ...) ...)
    (try! (add-stx-redeemable (get stacked-tokens vault)))
    ...

Impact: While this is likely intentionally permissionless (anyone can trigger the release as a protocol maintenance action), the function alters global protocol state (stx-redeemable) without authorization. The timing of when STX becomes redeemable could be strategically manipulated — an attacker could call it immediately at the unlock height to front-run other users in the xSTX redemption queue.

Recommendation: If intentionally permissionless, document this design decision. Otherwise, restrict to DAO owner, guardian, or liquidator.

MEDIUM

M-03: Pre-Clarity 4 as-contract — Blanket Asset Authority

Location: Multiple functions: collateralize-and-mint, pay-stability-fee, redeem-tokens, migrate-funds

Description: The contract uses pre-Clarity 4 as-contract which grants blanket authority over all assets held by the contract principal. Any contract that can induce a call path through Freddie's as-contract blocks could potentially move arbitrary assets.

;; In collateralize-and-mint:
(try! (as-contract (contract-call? .arkadiko-dao mint-token .usda-token debt sender)))

;; In pay-stability-fee:
(try! (contract-call? .usda-token transfer fee tx-sender (as-contract tx-sender) none))

;; In redeem-tokens:
(try! (as-contract (contract-call? .arkadiko-token transfer diko-amount tx-sender ... none)))
(as-contract (contract-call? .usda-token transfer usda-amount tx-sender ... none))

Impact: If any of the called contracts (or contracts they call) were malicious or compromised, they could drain all USDA, DIKO, or other assets held by Freddie during an as-contract execution. The DAO registry validation mitigates this significantly, but the blanket authority remains a structural risk.

Recommendation: Migrate to Clarity 4 as-contract? with explicit asset allowances: (as-contract? (with-ft .usda-token) (contract-call? ...))

LOW

L-01: Linear Stability Fee Model — Predictable Fee Avoidance

Location: stability-fee-helper function

Description: Stability fees are calculated as simple linear interest: blocks × (debt × fee / 10^decimals). This means fees don't compound, and users who frequently interact with their vaults (triggering fee accrual and payment) pay the same as those who don't.

(define-private (stability-fee-helper ...)
  (let (
    (number-of-blocks (- block-height stability-fee-last-accrued))
    (interest (/ (* debt fee) (pow u10 decimals)))
  )
    (ok (* number-of-blocks interest))
  )
)

Impact: The linear model slightly disadvantages the protocol compared to compound interest. Over long periods, the protocol collects less in fees than a compound model would. Combined with H-02 (fee erasure via mint), sophisticated users can minimize fee obligations significantly.

Recommendation: Acceptable design trade-off for on-chain gas efficiency. Document the model choice.

LOW

L-02: Integer Division Precision Loss in Collateral Ratio

Location: calculate-current-collateral-to-debt-ratio

Description: The collateral-to-debt ratio is computed with nested integer divisions, causing truncation at each step:

(/ (/ (* (get collateral vault) (get last-price price))
      (+ (get debt vault) ...))
   (/ (get decimals price) u100))

Impact: The outer division by (/ decimals u100) itself truncates. When decimals is not evenly divisible by 100, the denominator is slightly wrong. For typical oracle decimals (1000000), this works correctly (1000000/100 = 10000), but non-standard decimal values could produce incorrect ratios, potentially allowing under-collateralized minting or blocking valid withdrawals.

Recommendation: Use a single division with multiplied numerator/denominator to minimize truncation steps.

INFO

I-01: Pre-Clarity 4 Contract

Description: This contract predates Clarity 4 (epoch 3.3). It cannot use as-contract? with explicit asset allowances, contract-hash?, current-contract, or other safety builtins introduced in Clarity 4. This is expected for a contract deployed in 2021–2022 but represents a structural limitation.

INFO

I-02: Hardcoded Stacker Name Limit

Description: The contract initializes exactly 4 stacker slots (stacker through stacker-4) and validates set-stacking-unlock-burn-height against these 4 names. The protocol cannot add more stacker contracts without deploying a new version of Freddie. This is a known scalability limitation.

INFO

I-03: No Minimum Debt or Collateral Enforcement

Description: The collateralize-and-mint function does not enforce minimum debt or collateral amounts. A user could create a vault with 1 µSTX collateral and corresponding minimal debt. While the collateral ratio check limits the debt per collateral, dust vaults could accumulate in the vault data contract, increasing storage costs and complicating liquidation economics (gas cost to liquidate exceeds recovered value).

Architecture Assessment

Freddie is well-architected for a pre-Clarity 4 contract:

  • Separation of concerns: Vault data, reserves, oracle, collateral types, and liquidation are all separate contracts with trait-based interfaces
  • DAO registry validation: Every public function validates trait parameters against arkadiko-dao's registry, preventing malicious contract injection
  • Emergency shutdown: Dual-layer shutdown (DAO-level + Freddie-specific) on all state-changing functions
  • Migration support: migrate-funds and migrate-state enable smooth upgrades
  • Owner checks: Present on deposit, withdraw, mint, burn, toggle-stacking, stack-collateral — but notably missing on close-vault

Summary

Arkadiko Freddie v1-1 is a production-quality vault manager that has been live on Stacks mainnet since early in the protocol's history. The two high-severity findings — missing owner check on close-vault and stability fee erasure in mint — represent meaningful risks but are bounded: close-vault returns funds to the rightful owner (just forces the closure), and fee erasure benefits vault holders at the protocol's expense rather than enabling outright theft.

The contract's strongest defense is its comprehensive DAO registry validation — every trait parameter is checked against the authorized contract list, making malicious contract injection extremely difficult. The pre-Clarity 4 as-contract blanket authority is the primary structural risk, mitigated by the registry pattern.

Note: This contract has been superseded by later versions in the Arkadiko protocol. These findings apply to the v1-1 code as deployed on mainnet.
