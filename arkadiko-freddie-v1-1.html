Overview

Freddie is the core vault manager for Arkadiko — a MakerDAO-style CDP protocol on Stacks. Users deposit STX (or SIP-010 tokens) as collateral to mint USDA stablecoins. The contract handles vault lifecycle: creation, deposits, withdrawals, minting additional debt, burning debt, closing vaults, liquidation flows, and stability fee collection. It also integrates with Stacks' Proof-of-Transfer (PoX) stacking, allowing vault collateral to earn BTC yield.

At ~750 lines, this is a complex, high-value contract that sits at the center of Arkadiko's architecture, orchestrating interactions between the DAO, reserves (STX and SIP-010), oracle, vault data store, collateral types, auction engine, and vault rewards contracts.

Priority Score: 2.7 / 3.0

Financial=3 (DeFi/lending), Deploy=3 (mainnet since block 34,239), Complexity=3 (500+ lines, multi-contract orchestrator), Exposure=3 (Arkadiko is a major Stacks protocol), Novelty=1 (similar vault category already audited). Clarity version penalty: -0.5 → 2.2 (above 1.8 threshold).

Architecture

Freddie delegates nearly all state to external contracts:

  • arkadiko-vault-data-v1-1 — stores all vault state (owner, collateral, debt, flags)
  • arkadiko-dao — authorization registry, USDA mint/burn authority, emergency shutdown
  • arkadiko-stx-reserve-v1-1 / arkadiko-sip10-reserve-v1-1 — token custody
  • arkadiko-vault-rewards-v1-1 — DIKO reward tracking
  • Collateral types trait — per-type parameters (ratio, max debt, fees, liquidation penalty)
  • Oracle trait — price feeds for collateral valuation

Authorization for trait contracts (oracle, reserves, collateral-types) is validated via arkadiko-dao.get-qualified-name-by-name, providing upgradability through the DAO's contract registry.

Findings

HIGH

H-01: Missing owner check in close-vault — unauthorized vault closure

Location: close-vault function

Description: The close-vault function never verifies that tx-sender is the vault owner. Every other vault mutation function (deposit, withdraw, mint, toggle-stacking, stack-collateral) includes (asserts! (is-eq tx-sender (get owner vault)) (err ERR-NOT-AUTHORIZED)), but close-vault omits this check entirely.

(define-public (close-vault
  (vault-id uint)
  (reserve <vault-trait>)
  (ft <ft-trait>)
  (coll-type <collateral-types-trait>)
)
  (let ((vault (get-vault-by-id vault-id))
       (updated-vault (merge vault { collateral: u0, debt: u0, ... })))
    (asserts! (is-eq u0 (get stacked-tokens vault)) (err ERR-STACKING-IN-PROGRESS))
    ;; ... reserve and collateral-type checks ...
    ;; NO tx-sender == owner check!
    (if (is-eq (get debt vault) u0)
      true
      (try! (contract-call? .arkadiko-dao burn-token .usda-token (get debt vault) (get owner vault)))
    )
    (try! (contract-call? reserve burn ft (get owner vault) (get collateral vault)))
    ;; ...

Impact: If the DAO's burn-token function has blanket authority to burn USDA from any address (which is expected for a minter/burner contract), then anyone can force-close any non-stacking vault. This burns the owner's USDA without consent and returns their collateral. For zero-debt vaults, this unconditionally succeeds. An attacker could grief vault owners by closing their positions at disadvantageous times (e.g., right before a price increase that would have improved their ratio).

Recommendation: Add owner check: (asserts! (is-eq tx-sender (get owner vault)) (err ERR-NOT-AUTHORIZED))

HIGH

H-02: redeem-tokens has no access control — anyone can drain accumulated fees

Location: redeem-tokens function

Description: The function allows anyone to transfer arbitrary amounts of USDA and DIKO held by the contract to the DAO payout address. The only check is a 31-day cooldown since the last call. There is no restriction on who can call it or validation that the requested amounts are appropriate.

(define-public (redeem-tokens (usda-amount uint) (diko-amount uint))
  (begin
    (asserts! (> (- block-height (var-get block-height-last-paid)) (* BLOCKS-PER-DAY u31))
              (err ERR-NOT-AUTHORIZED))
    (var-set block-height-last-paid block-height)
    ;; transfers usda-amount and diko-amount to payout address
    ;; NO caller check!

Impact: While funds flow to the legitimate DAO payout address (not to the attacker), anyone can trigger fee distribution at will. An attacker could: (1) drain stability fee reserves before the protocol intends to use them, (2) front-run legitimate admin calls to reset the 31-day timer, or (3) strategically time fee distributions for MEV or governance manipulation. The caller also controls the exact amounts, which could be used to extract maximum available balances.

Recommendation: Add guardian or DAO owner check: (asserts! (is-eq tx-sender (contract-call? .arkadiko-dao get-dao-owner)) (err ERR-NOT-AUTHORIZED))

MEDIUM

M-01: Linear stability fee calculation undercharges over long periods

Location: stability-fee-helper function

Description: The stability fee is calculated as number-of-blocks × (debt × fee / 10^decimals) — a simple linear multiplication. This is a linear approximation of what should be compound interest. Over long periods (weeks to months), the protocol undercharges compared to true compounding.

(define-private (stability-fee-helper ...)
  (let (
    (number-of-blocks (- block-height stability-fee-last-accrued))
    (fee (get stability-fee collateral-type))
    (decimals (get stability-fee-decimals collateral-type))
    (interest (/ (* debt fee) (pow u10 decimals)))
  )
    (ok (* number-of-blocks interest))  ;; linear, not compounding
  ))

Impact: Revenue leakage for the protocol. For a 4% annual fee over 6 months without accrual, the difference between linear and compound is ~0.04% — small but non-zero. The accrue-stability-fee function helps mitigate this by allowing periodic checkpointing, but accrual is not automatic.

Recommendation: This is a known design trade-off in integer-only environments. Ensure accrue-stability-fee is called regularly (e.g., on every vault interaction) or when fee parameters change.

MEDIUM

M-02: release-stacked-stx is permissionless — anyone can trigger for any liquidated vault

Location: release-stacked-stx function

Description: The function has no caller restriction. Anyone can call it for any liquidated xSTX vault once the burn height is reached. While the comment says "method that can only be called by deployer (contract owner)", the code has no such check.

;; method that can only be called by deployer (contract owner)
;; unlocks STX that had their xSTX derivative liquidated in an auction
(define-public (release-stacked-stx (vault-id uint))
  ;; NO caller check — anyone can call
  (let ((vault (get-vault-by-id vault-id)))
    ;; validates: not shutdown, xSTX collateral, is-liquidated, has stacked tokens, burn height reached
    (try! (add-stx-redeemable (get stacked-tokens vault)))
    ;; ...

Impact: Not directly exploitable since it only makes STX redeemable (a helpful action), but it contradicts the documented access control intent. In a multi-contract system, permissionless state transitions can have unexpected downstream effects.

Recommendation: Either add the intended deployer/guardian check or update the documentation to reflect the permissionless design as intentional.

MEDIUM

M-03: Pre-Clarity 4 as-contract grants blanket asset authority

Location: Multiple functions: collateralize-and-mint, pay-stability-fee, redeem-tokens, migrate-funds, get-usda-balance, get-diko-balance

Description: The contract uses as-contract (pre-Clarity 4) for token operations including minting USDA, transferring USDA/DIKO fees, and migrating funds. Pre-Clarity 4 as-contract gives the enclosed expression blanket authority over all assets held by the contract principal — there is no way to restrict which tokens or amounts can be moved.

;; Mints USDA to user
(try! (as-contract (contract-call? .arkadiko-dao mint-token .usda-token debt sender)))

;; Transfers stability fees
(try! (contract-call? .usda-token transfer fee tx-sender (as-contract tx-sender) none))

;; Migrate ALL tokens to new contract — blanket authority
(as-contract (contract-call? token transfer balance tx-sender (contract-of new-vault-manager) none))

Impact: If any function in this contract has an exploitable path that reaches an as-contract block, the attacker gains full control over all assets held by the contract. Clarity 4's as-contract? with explicit with-ft/with-stx allowances would limit blast radius.

Recommendation: When upgrading to a future Freddie version, use Clarity 4 as-contract? with explicit asset allowances (e.g., (as-contract? (with-ft .usda-token) ...)).

LOW

L-01: toggle-freddie-shutdown uses toggle pattern — accidental re-enable risk

Location: toggle-freddie-shutdown function

Description: The emergency shutdown is a boolean toggle rather than an explicit set. In an emergency, the guardian calls toggle to activate shutdown. A second accidental call re-enables the contract.

(define-public (toggle-freddie-shutdown)
  (begin
    (asserts! (is-eq tx-sender (contract-call? .arkadiko-dao get-guardian-address)) (err ERR-NOT-AUTHORIZED))
    (ok (var-set freddie-shutdown-activated (not (var-get freddie-shutdown-activated))))
  ))

Impact: Low — the guardian is a trusted role. But in a crisis, a duplicate transaction (e.g., from retry logic) could accidentally deactivate the shutdown.

Recommendation: Use separate activate-shutdown / deactivate-shutdown functions, or at minimum an explicit set: (set-freddie-shutdown (active bool)).

LOW

L-02: deposit doesn't update stacked-tokens — collateral/stacking mismatch

Location: deposit function

Description: When a user deposits additional collateral into a vault that has active stacking, the collateral field increases but stacked-tokens is not updated. The vault's collateral-to-debt ratio improves on paper, but the additional STX may not actually be stacked until the next cycle.

(define-public (deposit (vault-id uint) (uamount uint) ...)
  (let (
    (new-collateral (+ uamount (get collateral vault)))
    (updated-vault (merge vault {
      collateral: new-collateral,
      updated-at-block-height: block-height
      ;; stacked-tokens NOT updated
    }))
  ) ...

Impact: The collateral amount and stacked amount can diverge. This is likely intentional (new deposits are stacked in the next cycle via stack-collateral), but the asymmetry means the vault may appear healthier than it is from a liquidity perspective.

Recommendation: Document this behavior. Consider tracking "unstacked collateral" separately for transparency.

INFO

I-01: Pre-Clarity 4 contract — no access to modern safety builtins

Description: Deployed at Stacks block 34,239 (very early mainnet), this contract predates Clarity 4 (epoch 3.3, Bitcoin block 923,222). It cannot use as-contract? with explicit asset allowances, contract-hash?, restrict-assets?, or other safety improvements. This is inherent to the deployment era and cannot be fixed without redeployment.

INFO

I-02: Extensive unwrap-panic usage for DAO registry lookups

Description: The contract uses unwrap-panic throughout for DAO registry lookups (get-qualified-name-by-name, get-emergency-shutdown-activated, etc.). If any DAO registry entry is missing or the DAO contract is misconfigured, the entire transaction aborts with a panic rather than returning a meaningful error. This is a pragmatic choice (these lookups should never fail in production), but it means DAO misconfiguration would brick all vault operations simultaneously.

INFO

I-03: migrate-funds transfers all tokens of any type to a new vault manager

Description: The migrate-funds function accepts an arbitrary ft-trait token and transfers the contract's entire balance to a new vault manager. While gated to the DAO owner, this gives a single key the ability to move all contract-held tokens to any contract implementing the vault manager trait. This is standard for upgradable protocols but represents significant trust centralization.

(define-public (migrate-funds (new-vault-manager <vault-manager-trait>) (token <ft-trait>))
  (begin
    (asserts! (is-eq contract-caller (contract-call? .arkadiko-dao get-dao-owner)) (err ERR-NOT-AUTHORIZED))
    (let ((balance (unwrap-panic (contract-call? token get-balance (as-contract tx-sender)))))
      (as-contract (contract-call? token transfer balance tx-sender (contract-of new-vault-manager) none))
    )))

Positive Observations

  • Comprehensive trait validation — every public function that accepts trait parameters validates them against the DAO's contract registry, preventing rogue contract injection.
  • Clean separation of concerns — vault state, reserves, rewards, and collateral types are all in separate contracts. Freddie is a pure orchestration layer.
  • Emergency shutdown — dual-layer shutdown (DAO-level + Freddie-specific) provides defense in depth.
  • PoX integration — sophisticated stacking lifecycle management with proper unlock height tracking per stacker contract.
  • Collateral type extensibility — the trait-based collateral type system allows adding new collateral types without redeploying Freddie.
  • Stability fee accrual — the accrue-stability-fee function allows fee checkpointing when parameters change, preventing retroactive fee changes.

Summary

Arkadiko Freddie v1-1 is a well-architected vault manager with strong separation of concerns and comprehensive authorization checks via the DAO registry. The two High findings — missing owner check on close-vault and permissionless redeem-tokens — are meaningful access control gaps but not catastrophic: close-vault returns collateral to the rightful owner, and redeem-tokens sends fees to the legitimate DAO payout address. The pre-Clarity 4 as-contract blanket authority is the most architecturally significant concern for any future exploit path. Overall, this is production-quality code from the early Stacks era with minor access control oversights.
