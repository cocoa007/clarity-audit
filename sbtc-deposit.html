sBTC Deposit — Security Audit

SM3VDXK3WZZSA84XXFKAFAF15NNZX32CTSG82JFQ4.sbtc-deposit
Audited: 2026-02-27 · Clarity version: pre-Clarity 4 · Confidence: Medium

Overview

The sBTC deposit contract is part of the sBTC protocol — the trust-minimized Bitcoin peg on Stacks. It validates and processes Bitcoin deposits by minting sBTC tokens to recipients after the signer set confirms the deposit on-chain.

Source: On-chain (Hiro Explorer)

Architecture: The deposit flow works as follows: (1) User sends BTC to the sBTC peg address on Bitcoin, (2) sBTC signers observe the deposit and call complete-deposit-wrapper on Stacks, (3) the contract validates the deposit, mints sBTC to the recipient, and records it in sbtc-registry. The signer set (multisig) is fully trusted to submit correct deposit data. Key contracts: sbtc-deposit (validates and mints), sbtc-registry (state management, protocol roles), sbtc-token (SIP-010 fungible token).

Trust model: Signers are trusted to provide correct amount, recipient, burn-hash, burn-height, and sweep-txid. No on-chain SPV proof of the Bitcoin transaction exists — the system relies entirely on signer honesty.

Findings

H-01 — No Guard Against maxFee ≥ Amount — Deposits Become Unprocessable

Location: complete-deposit-wrapper — missing validation

The contract accepts any amount ≥ 546 (dust limit) but has no concept of fees or minimum net amount. In the sBTC protocol, Bitcoin deposits include a max_fee parameter set by the user. If max_fee >= amount, the sBTC signers will skip the deposit because there would be zero or negative sBTC to mint after fees.

This results in permanently stuck BTC: the Bitcoin is sent to the peg address, but signers will never call complete-deposit-wrapper for it. The BTC cannot be recovered until the reclaim height is reached (150 blocks).

Real-world impact: We personally experienced this — 5,000 sats stuck in a deposit where maxFee = 5,000 (equal to amount). The signers simply never processed it. The BTC sits in the peg address until the reclaim height at BTC block 938,775.

Recommendation:

  • The deposit request script on Bitcoin should enforce max_fee < amount - dust_limit
  • Alternatively, signers should process deposits by minting amount - max_fee even if the result is small
  • Front-end UIs must validate max_fee < amount before broadcasting
  • Document the reclaim mechanism more prominently for stuck deposits

M-01 — Batch Deposit Failure Aborts All Subsequent Deposits

Location: complete-individual-deposits-helper

The complete-deposits-wrapper uses fold with a helper function. If any individual deposit fails (replay, bad burn hash, etc.), the error propagates and all subsequent deposits in the batch are skipped.

(match helper-response
  index (begin
    (unwrap! (complete-deposit-wrapper ...)
      (err (+ ERR_DEPOSIT_INDEX_PREFIX (+ u10 index))))
    (ok (+ index u1)))
  err-response (err err-response))

A single invalid deposit in a batch blocks all deposits after it. Signers must carefully order/filter deposits or retry with the failing deposit removed.

Recommendation: Use a "skip on error" pattern — return (ok) with an error log for failed individual deposits, allowing the fold to continue processing remaining deposits.

M-02 — No Maximum Amount Cap on Deposits

Location: complete-deposit-wrapper — amount validation

The contract only enforces amount >= dust-limit (546 sats) with no upper bound. A compromised or buggy signer could mint an arbitrary amount of sBTC in a single transaction.

Recommendation: Add a per-deposit cap as a safety rail (e.g., 2,100,000,000,000,000 sats = 21M BTC). This limits blast radius from key compromise.

L-01 — Error Code Collision in Batch Deposits

Location: complete-individual-deposits-helper

Error encoding is ERR_DEPOSIT_INDEX_PREFIX + 10 + index. With prefix u303, errors range u313–u813 for up to 500 items, which could theoretically overlap with other protocol error codes.

Recommendation: Use a dedicated error range (e.g., u10000 + index) to avoid collision.

L-02 — No Event Emission in Deposit Contract

Location: complete-deposit-wrapper

The deposit contract itself emits no print events. Events are only emitted by sbtc-registry.complete-deposit. A failed registry call after successful mint would leave inconsistent state with no deposit event.

Recommendation: Emit a print event in the deposit contract for better observability.

I-01 — Pre-Clarity 4 Contract Patterns

Location: Contract-wide

Uses .sbtc-registry and .sbtc-token relative references. Does not use Clarity 4's as-contract? with explicit asset allowances. While this contract doesn't use as-contract at all, future upgrades should adopt Clarity 4 patterns.

I-02 — Signer Principal is Single Point of Trust

Location: current-signer-principal check

The current-signer-principal is a single address representing the multisig signer set. Key rotation is handled by sbtc-registry.rotate-keys. This is the intended sBTC design — the signer set is the root of trust.

Recommendation: Consider time-locked minting caps as defense-in-depth against key compromise.

I-03 — No Recipient Validation

Location: complete-deposit-wrapper — recipient parameter

The recipient is an unchecked principal. Signers could accidentally or maliciously mint sBTC to any address, including contracts or burn addresses.

Recommendation: Consider basic validation (e.g., recipient is a standard principal, not a contract) if deposits are intended only for user wallets.

Cross-Contract Analysis

sbtc-registry: Role-based access via active-protocol-contracts map. Bidirectional check in is-protocol-caller. Replay protection via map-insert for deposit status. Key rotation has aggregate-pubkeys replay protection.

sbtc-token: Protocol functions gated by sbtc-registry.is-protocol-caller. No supply cap by design (sBTC supply = pegged BTC). SIP-010 transfer correctly checks sender authorization.

Overall Assessment

The sbtc-deposit contract is well-structured and minimal — ~90 lines of logic doing one thing well. The main risks are at the protocol level:

  • H-01: The maxFee ≥ amount issue leads to permanent fund loss with no clear reclaim path — this is the most impactful real-world finding
  • M-01: All-or-nothing batch semantics could cause operational deposit processing delays
  • Trust: The entire system trusts the signer set — standard for sBTC's design

No reentrancy risks (Clarity prevents by design). No as-contract usage means no asset authority concerns. The contract is solid for its scope — the gaps are at the protocol/UX layer.
