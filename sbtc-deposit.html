Overview

The sBTC deposit contract handles the Stacks-side completion of BTC-to-sBTC deposits. When a user sends BTC to the sBTC peg address on Bitcoin, the sBTC signer set (a multisig) observes the deposit and calls this contract to mint the corresponding sBTC tokens on Stacks.

Architecture

  • Deposit validation: Checks caller is current signer principal, amount ≥ dust limit (546 sats), TXID = 32 bytes, no replay, burn header hash matches
  • Minting: Calls sbtc-token.protocol-mint to create sBTC for the recipient
  • State: Records deposits in sbtc-registry for replay protection
  • Batch support: complete-deposits-wrapper processes up to 500 deposits via fold
  • Trust model: Signers are fully trusted — no on-chain SPV verification of Bitcoin transactions

Findings

HIGH

H-01: No Guard Against maxFee ≥ Amount — Deposits Become Unprocessable

Location: complete-deposit-wrapper — missing validation

The contract accepts any amount ≥ 546 (dust limit) but has no concept of fees or minimum net amount. In the sBTC protocol, Bitcoin deposits include a max_fee parameter set by the user. If max_fee ≥ amount, signers will skip the deposit because there would be zero or negative sBTC to mint after fees.

This results in permanently stuck BTC: the Bitcoin is sent to the peg address, but signers will never call complete-deposit-wrapper for it. The BTC sits in the peg address with no reclaim mechanism until the reclaim height is reached.

Real-world impact: We personally experienced this — 5,000 sats stuck in a deposit where maxFee = 5,000 (equal to the deposit amount). The signers simply never processed it. The BTC is reclaimable only after ~6 days at a specific Bitcoin block height.

Recommendation:

  • The Bitcoin-side deposit script should enforce max_fee < amount - dust_limit
  • Signers should process these deposits by minting amount - actual_fee rather than skipping entirely
  • Front-end UIs should validate max_fee < amount before broadcasting
  • Consider an on-chain reclaim/refund mechanism for unprocessable deposits
MEDIUM

M-01: Batch Deposit Failure Aborts All Subsequent Deposits

Location: complete-individual-deposits-helper

The complete-deposits-wrapper uses fold with a helper function. If any individual deposit fails (e.g., replay, bad burn hash), the error propagates and all subsequent deposits in the batch are skipped.

(match helper-response
  index (begin (unwrap! (complete-deposit-wrapper ...) (err ...)) (ok (+ index u1)))
  err-response (err err-response))

A single invalid deposit in a batch of 500 blocks all deposits after it. This is a DoS vector on deposit throughput — signers must carefully filter/order deposits.

Recommendation: Use a "skip on error" pattern — return (ok) with an error log for failed individual deposits, allowing the fold to continue.

MEDIUM

M-02: No Maximum Amount Cap on Deposits

Location: complete-deposit-wrapper — amount validation

Only amount ≥ dust_limit (546 sats) is enforced, with no upper bound. A compromised signer could mint unlimited sBTC in a single transaction.

While inherent to the trust model (signers are trusted), a sanity cap would limit blast radius from key compromise or bugs.

Recommendation: Add a per-deposit cap as defense-in-depth (e.g., 2,100,000,000,000,000 sats = 21M BTC).

LOW

L-01: Error Code Collision in Batch Deposits

Location: complete-individual-deposits-helper

Error encoding is ERR_DEPOSIT_INDEX_PREFIX + 10 + index (prefix = u303). For large batches, these could theoretically collide with other protocol error codes.

Recommendation: Use a dedicated error range (e.g., u10000 + index) to avoid collision.

LOW

L-02: No Event Emission in Deposit Contract

Location: complete-deposit-wrapper

The deposit contract emits no print events. Events are only emitted by sbtc-registry.complete-deposit. A failed registry call after successful mint would leave an inconsistent state with no deposit event.

Recommendation: Emit a print event in the deposit contract for better observability.

INFO

I-01: Pre-Clarity 4 — Legacy Contract Call Patterns

Uses .sbtc-registry and .sbtc-token relative references without Clarity 4's as-contract? with explicit asset allowances. Future upgrades should adopt Clarity 4 patterns.

INFO

I-02: Signer Principal is Single Point of Trust

The current-signer-principal is a single address (representing the multisig signer set). Key rotation is handled by sbtc-registry.rotate-keys. If compromised, unlimited minting is possible.

Recommendation: Consider time-locked minting caps as defense-in-depth.

INFO

I-03: No Recipient Validation

The recipient parameter is an unchecked principal. Signers could mint sBTC to any address, including the contract itself or burn addresses. Consider basic validation if deposits are intended only for user wallets.

Overall Assessment

The sbtc-deposit contract is well-structured and minimal — ~90 lines of logic doing one thing (validate and mint deposits) with appropriate access control. No reentrancy risks (Clarity prevents this by design). No as-contract usage means no asset authority concerns.

The main risks are:

  1. Protocol-level gap (H-01): The maxFee ≥ amount issue leads to permanent fund loss with no reclaim path. This is the most impactful real-world problem.
  2. Batch processing (M-01): All-or-nothing batch semantics could cause operational issues and throughput degradation.
  3. Trust concentration (I-02): The entire system trusts the signer set — standard for sBTC's design but limits defense-in-depth.

Rating: The contract itself is solid for its scope. The critical gap is at the protocol level — the lack of protection against unprocessable deposits and the absence of a user-friendly reclaim mechanism.
