sBTC Deposit — Security Audit

SM3VDXK3WZZSA84XXFKAFAF15NNZX32CTSG82JFQ4.sbtc-deposit
Audited: 2026-02-27 · Clarity version: pre-Clarity 4 · Confidence: Medium

Overview

The sBTC deposit contract is the entry point for the sBTC protocol — the Bitcoin-backed token on Stacks. It validates deposit parameters from trusted signers and mints sBTC to recipients. The contract is part of a multi-contract system including sbtc-registry (state management) and sbtc-token (SIP-010 token).

Source: On-chain (Hiro Explorer)

Architecture: The deposit flow is: (1) User sends BTC to the sBTC peg address on Bitcoin, (2) sBTC signers observe the deposit and call complete-deposit-wrapper on Stacks, (3) The contract validates the deposit, mints sBTC via sbtc-token, and records it in sbtc-registry. The signer set (multisig) is fully trusted — no SPV proof of Bitcoin transactions is performed on-chain.

Findings

H-01 — No Guard Against maxFee ≥ Amount — Deposits Become Unprocessable

Location: complete-deposit-wrapper — missing validation

The contract accepts any amount ≥ 546 (dust limit) but has no concept of fees or minimum net amount. In the sBTC protocol, Bitcoin deposits include a max_fee parameter set by the user. If max_fee >= amount, the sBTC signers will skip the deposit because there would be zero or negative sBTC to mint after fees.

This results in permanently stuck BTC: the Bitcoin is sent to the peg address, but signers will never call complete-deposit-wrapper for it because the economics don't work. The BTC cannot be recovered until the reclaim locktime expires.

Real-world impact: We personally experienced this — 5,000 sats stuck in a deposit where maxFee = amount. The signers simply never process it. The BTC sits locked until the reclaim script timelock expires (typically ~150 blocks after the deposit lock period).

Recommendation:

  • The deposit request script on Bitcoin should enforce max_fee < amount - dust_limit at the script level
  • Signers should process these deposits by minting amount - max_fee (even if tiny) rather than silently skipping them
  • A reclaim/refund mechanism should exist for deposits that signers cannot or will not process
  • Front-end UIs should validate max_fee < amount before broadcasting

M-01 — Batch Deposit Failure Aborts All Subsequent Deposits

Location: complete-individual-deposits-helper

The complete-deposits-wrapper uses fold with a helper function. If any individual deposit fails (replay, bad burn hash, etc.), the error propagates and all subsequent deposits in the batch are skipped.

(match helper-response
  index
    (begin
      (unwrap!
        (complete-deposit-wrapper ...)
      (err (+ ERR_DEPOSIT_INDEX_PREFIX (+ u10 index))))
      (ok (+ index u1))
    )
  err-response
    (err err-response)
)

Impact: A single invalid deposit in a batch blocks all deposits after it. Signers must carefully order/filter deposits, or retry with the failing deposit removed. This is a DoS vector on deposit throughput.

Recommendation: Use a "skip on error" pattern — return (ok) with an error log for failed individual deposits, allowing the fold to continue processing remaining deposits.

M-02 — No Maximum Amount Cap on Deposits

Location: complete-deposit-wrapper — amount validation

The contract only enforces amount >= dust-limit (546 sats) with no upper bound. A compromised or buggy signer could mint an arbitrary amount of sBTC in a single transaction.

Impact: If the signer key is compromised, an attacker can mint unlimited sBTC. While this is inherent to the trust model, a sanity cap would limit blast radius.

Recommendation: Add a reasonable per-deposit cap as a safety rail (e.g., 2,100,000,000,000,000 sats = 21M BTC). This limits damage from key compromise or bugs.

L-01 — Error Code Collision in Batch Deposits

Location: complete-individual-deposits-helper

The error encoding is ERR_DEPOSIT_INDEX_PREFIX + 10 + index. ERR_DEPOSIT_INDEX_PREFIX is u303. For large batches, these could theoretically collide with other protocol error codes.

Recommendation: Use a dedicated error range (e.g., u10000 + index) to avoid any possible collision.

L-02 — No Event Emission in Deposit Contract

Location: complete-deposit-wrapper

The deposit contract itself emits no print events. Events are only emitted by sbtc-registry.complete-deposit. If the registry call fails after minting, the mint event exists but no deposit-completion event is emitted.

Recommendation: Emit a print event in the deposit contract itself for better observability.

I-01 — Pre-Clarity 4 Contract Patterns

Location: Contract-wide

The contract uses .sbtc-registry and .sbtc-token relative references and does not use Clarity 4's as-contract? with explicit asset allowances. Future upgrades should adopt Clarity 4 patterns for improved safety.

I-02 — Signer Principal is Single Point of Trust

Location: Access control

The current-signer-principal is a single address representing the multisig output. On-chain it appears as a single principal. Key rotation is handled by sbtc-registry.rotate-keys (governance-only). This is the intended design but represents total trust concentration.

Recommendation: Consider time-locked minting caps as defense-in-depth.

I-03 — No Recipient Validation

Location: complete-deposit-wrapper

The recipient parameter is an unchecked principal. Signers could (accidentally or maliciously) mint sBTC to any address, including the contract itself or burn addresses.

Recommendation: Consider basic validation (e.g., recipient is a standard principal, not a contract principal).

Cross-Contract Analysis

The deposit contract interacts with two companion contracts:

  • sbtc-registry — Role-based access via active-protocol-contracts map. Bidirectional protocol caller check. map-insert for deposit status ensures replay protection.
  • sbtc-token — Protocol functions gated by registry. protocol-mint has no supply cap (by design — sBTC supply = pegged BTC). SIP-010 transfer correctly validates sender authorization.

Overall Assessment

The sbtc-deposit contract is well-structured and minimal — it does one thing (validate and mint deposits) with appropriate access control. The main risks are:

  1. Protocol-level gap: The maxFee ≥ amount issue (H-01) leads to permanent fund loss with no reclaim path — this is the most impactful real-world finding
  2. Batch processing: The all-or-nothing batch semantics (M-01) could cause operational issues under load
  3. Trust concentration: The entire system trusts the signer set — standard for sBTC's design but worth noting

The contract is lean (~90 lines of logic) which limits attack surface. No reentrancy risks (Clarity prevents this by design). No as-contract usage means no asset authority concerns.
