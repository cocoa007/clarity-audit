Architecture

The sBTC deposit flow works as follows:

  1. User sends BTC to the sBTC peg address on Bitcoin
  2. sBTC signers (off-chain multisig) observe the deposit and call complete-deposit-wrapper on Stacks
  3. The contract validates the deposit, mints sBTC to the recipient, and records it in sbtc-registry

Trust model: The signer set is fully trusted to submit correct deposit data. The contract validates: caller is current signer principal, amount ≥ dust limit (546 sats), TXID length = 32 bytes, no replay (deposit not already completed), burn header hash matches (Bitcoin fork protection).

Key contracts: sbtc-deposit (validates and mints), sbtc-registry (stores state, manages roles), sbtc-token (SIP-010 fungible token with protocol-gated mint/burn).

Findings

HIGH H-01: No Guard Against maxFee ≥ Amount — Deposits Become Unprocessable

Location: complete-deposit-wrapper — missing validation

The contract accepts any amount ≥ 546 (dust limit) but has no concept of fees or minimum net amount. In the sBTC protocol, Bitcoin deposits include a max_fee parameter set by the user. If max_fee >= amount, the sBTC signers will skip the deposit because there would be zero or negative sBTC to mint after fees.

This results in permanently stuck BTC: the Bitcoin is sent to the peg address, but signers will never call complete-deposit-wrapper for it. The BTC cannot be recovered until the reclaim height (set at deposit time).

Real-world impact: We personally experienced this — 5,000 sats stuck in a deposit where maxFee = amount. The signers simply never process it. Recovery requires waiting ~6 days for the reclaim block height.

Recommendation:

  • The deposit request script on Bitcoin should enforce max_fee < amount - dust_limit
  • Signers should process these deposits by minting amount - max_fee (even if tiny) rather than silently skipping
  • Front-end UIs should validate max_fee < amount before broadcasting
MEDIUM M-01: Batch Deposit Failure Aborts All Subsequent Deposits

Location: complete-individual-deposits-helper

The complete-deposits-wrapper uses fold with a helper. If any individual deposit fails (replay, bad burn hash), the error propagates and all subsequent deposits in the batch are skipped.

(match helper-response
  index
    (begin
      (unwrap!
        (complete-deposit-wrapper ...)
      (err (+ ERR_DEPOSIT_INDEX_PREFIX (+ u10 index))))
      (ok (+ index u1))
    )
  err-response
    (err err-response)
)

A single invalid deposit in a batch blocks all deposits after it. Signers must carefully filter deposits or retry with the failing one removed.

Recommendation: Use a "skip on error" pattern — return (ok) with an error log for failed deposits, allowing the fold to continue.

MEDIUM M-02: No Maximum Amount Cap on Deposits

Location: complete-deposit-wrapper — amount validation

Only enforces amount >= dust-limit with no upper bound. A compromised signer could mint arbitrary sBTC in a single transaction. While inherent to the trust model, a sanity cap would limit blast radius.

Recommendation: Add a per-deposit cap as defense-in-depth (e.g., 21M BTC equivalent in sats).

LOW L-01: Error Code Collision in Batch Deposits

Error encoding is ERR_DEPOSIT_INDEX_PREFIX + 10 + index (base 303). For large batches this could collide with other error codes, though the list is capped at 500 items.

Recommendation: Use a dedicated error range (e.g., u10000 + index).

LOW L-02: No Event Emission in Deposit Contract

The deposit contract emits no print events. Events are only emitted by sbtc-registry.complete-deposit. If the registry call fails after minting, no deposit-completion event is emitted.

Recommendation: Emit a print event in the deposit contract for observability.

INFO I-01: Pre-Clarity 4 Patterns

Uses legacy .sbtc-registry relative references. Does not use Clarity 4's as-contract? with explicit asset allowances. Upgrade path should adopt Clarity 4.

INFO I-02: Signer Principal is Single Point of Trust

The current-signer-principal is checked via is-eq tx-sender. This represents the multisig signer set. Standard for sBTC design but worth noting — key compromise enables unlimited minting.

INFO I-03: No Recipient Validation

The recipient parameter is an unchecked principal. Signers could mint sBTC to any address including contracts or burn addresses. Low likelihood given trusted signers.

Cross-Contract Notes

  • sbtc-registry: Role-based access via active-protocol-contracts map with bidirectional check — well-designed. map-insert for deposit-status provides correct replay protection.
  • sbtc-token: Protocol functions gated by sbtc-registry.is-protocol-caller. No supply cap by design (sBTC supply = pegged BTC). SIP-010 transfer correctly validates sender authorization.

Overall Assessment

The sbtc-deposit contract is well-structured and minimal (~90 lines of logic). It does one thing — validate and mint deposits — with appropriate access control. No reentrancy risks (Clarity prevents this). No as-contract usage means no asset authority concerns.

The most impactful finding (H-01) is a protocol-level issue: the lack of protection against deposits where maxFee ≥ amount, leading to permanently stuck BTC until the reclaim height. This is validated by personal experience — 5,000 sats stuck for 6+ days.

The batch processing issue (M-01) could affect deposit throughput during high-volume periods. The missing amount cap (M-02) is defense-in-depth for the trust model.
