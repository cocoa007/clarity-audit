sBTC Deposit — Security Audit

SM3VDXK3WZZSA84XXFKAFAF15NNZX32CTSG82JFQ4.sbtc-deposit
Audited: 2026-02-27 · Clarity version: pre-Clarity 4 · Confidence: Medium

Overview

The sBTC deposit contract handles the Stacks-side completion of Bitcoin-to-sBTC deposits. When a user sends BTC to the sBTC peg address, the sBTC signer set observes the deposit and calls this contract to mint sBTC to the recipient.

Source: On-chain (Hiro Explorer)

Architecture: The deposit flow is signer-initiated: (1) user sends BTC to peg address on Bitcoin, (2) sBTC signers observe and call complete-deposit-wrapper on Stacks, (3) contract validates caller is current signer principal, verifies dust limit, checks for replay, validates burn header hash, then mints sBTC via sbtc-token and records in sbtc-registry. Batch processing is supported via complete-deposits-wrapper.

Trust model: The signer set (multisig) is fully trusted to submit correct deposit data. No on-chain SPV proof of the Bitcoin transaction — the contract relies entirely on signer honesty.

Findings

H-01 — No Guard Against maxFee ≥ Amount — Deposits Become Unprocessable

Location: complete-deposit-wrapper — missing validation

The contract accepts any amount ≥ 546 (dust limit) but has no concept of fees or minimum net amount. In the sBTC protocol, Bitcoin deposits include a max_fee parameter set by the user. If max_fee >= amount, the sBTC signers skip the deposit because there would be zero or negative sBTC to mint after fees.

This results in permanently stuck BTC: the Bitcoin is sent to the peg address, but signers will never call complete-deposit-wrapper for it. The BTC cannot be recovered until the reclaim height is reached.

Real-world impact: We personally experienced this — 5,000 sats stuck in a deposit where maxFee = amount. The signers simply never process it. The only recovery path is waiting for the reclaim block height (~6 days).

Recommendation:

  • The deposit request script on Bitcoin should enforce max_fee < amount - dust_limit
  • Signers should process edge-case deposits by minting amount - actual_fee rather than skipping
  • Front-end UIs should validate max_fee < amount before broadcasting
  • A reclaim/refund mechanism documentation should be more prominent

M-01 — Batch Deposit Failure Aborts All Subsequent Deposits

Location: complete-individual-deposits-helper

The complete-deposits-wrapper uses fold with a helper function. If any individual deposit fails (replay, bad burn hash, etc.), the error propagates and all subsequent deposits in the batch are skipped.

(match helper-response
  index
    (begin
      (unwrap!
        (complete-deposit-wrapper ...)
      (err (+ ERR_DEPOSIT_INDEX_PREFIX (+ u10 index))))
      (ok (+ index u1))
    )
  err-response
    (err err-response)
)

A single invalid deposit in a batch blocks all deposits after it. Signers must carefully filter deposits or retry with the failing one removed.

Recommendation: Use a "skip on error" pattern — return (ok) with an error log for failed individual deposits, allowing the fold to continue.

M-02 — No Maximum Amount Cap on Deposits

Location: complete-deposit-wrapper — amount validation

The contract only enforces amount >= dust-limit (546 sats) with no upper bound. A compromised signer could mint arbitrary amounts of sBTC in a single transaction.

While this is inherent to the trust model, a sanity cap would limit blast radius from key compromise or bugs.

Recommendation: Add a per-deposit cap as a safety rail (e.g., 2,100,000,000,000,000 sats = 21M BTC).

L-01 — Error Code Collision Risk in Batch Deposits

Location: complete-individual-deposits-helper

Error encoding uses ERR_DEPOSIT_INDEX_PREFIX + 10 + index. With ERR_DEPOSIT_INDEX_PREFIX = u303, errors range from u313 upward. For large batches, these could theoretically collide with other protocol error codes.

Recommendation: Use a dedicated error range (e.g., u10000 + index) to avoid collisions.

L-02 — No Event Emission in Deposit Contract

Location: complete-deposit-wrapper

The deposit contract emits no print events. Events are only emitted by sbtc-registry.complete-deposit. If the registry call fails after minting, the mint event exists but no deposit-completion event is emitted.

Recommendation: Emit a print event in the deposit contract for better observability.

I-01 — Pre-Clarity 4 Contract Patterns

Location: Contract-wide

Uses .sbtc-registry and .sbtc-token relative references. Does not use Clarity 4's as-contract? with explicit asset allowances. Future upgrades should adopt Clarity 4 patterns.

I-02 — Signer Principal is Single Point of Trust

Location: Access control

The current-signer-principal appears as a single address on-chain (represents the multisig output). If compromised, unlimited minting is possible. This is the intended sBTC design — consider time-locked minting caps as defense-in-depth.

I-03 — No Recipient Validation

Location: complete-deposit-wrapper — recipient parameter

The recipient is an unchecked principal. Signers could mint sBTC to any address including contracts or burn addresses. Consider basic validation if deposits are intended only for user wallets.

Cross-Contract Analysis

sbtc-registry: Role-based access via active-protocol-contracts map. Bidirectional check in is-protocol-caller. Replay protection via map-insert for deposit status. Key rotation includes aggregate-pubkeys replay protection.

sbtc-token: Protocol mint/burn gated by registry. SIP-010 compliant. No supply cap by design (sBTC supply = pegged BTC). Transfer correctly checks tx-sender or contract-caller.

Overall Assessment

The sbtc-deposit contract is well-structured and minimal — ~90 lines of logic doing one thing (validate and mint deposits) with appropriate access control. The main risks are protocol-level rather than contract-level:

  • H-01 (maxFee ≥ amount) is the most impactful real-world issue — confirmed by personal experience with stuck funds
  • M-01 (batch abort) could cause operational throughput issues
  • Trust concentration in the signer set is by design but worth noting

No reentrancy risks (Clarity prevents this). No as-contract usage. The contract is lean and limited in attack surface.
