sBTC Protocol · SM3VDXK3WZZSA84XXFKAFAF15NNZX32CTSG82JFQ4 · Mainnet · 2026-02-27

Overview

The sBTC deposit contract handles the Stacks-side completion of Bitcoin-to-sBTC deposits. sBTC signers observe BTC deposits and call this contract to mint sBTC to the recipient. The contract validates caller authorization, prevents replay, and enforces a dust limit.

Architecture

The deposit flow: (1) User sends BTC to the sBTC peg address, (2) sBTC signers observe and call complete-deposit-wrapper on Stacks, (3) contract validates, mints sBTC via sbtc-token, records in sbtc-registry.

Trust model: Signer set (multisig) is fully trusted. Contract validates: caller = current signer principal, amount ≥ dust limit, TXID = 32 bytes, no replay, burn hash matches.

Findings

HIGH

H-01: No Guard Against maxFee ≥ Amount — Deposits Become Unprocessable

Location: complete-deposit-wrapper

The contract accepts any amount ≥ 546 (dust limit) but has no concept of fees. In the sBTC protocol, Bitcoin deposits include a max_fee parameter. If max_fee >= amount, signers skip the deposit because there would be zero or negative sBTC to mint. Nothing prevents users from setting max_fee >= amount.

Impact: Permanent fund loss. We personally experienced this: 5,000 sats stuck in a deposit where maxFee ≥ amount. Signers never process it. No reclaim mechanism exists. BTC is reclaimable only via the Bitcoin-side timelock (144+ blocks), which many users may not understand.

Recommendation: (1) Bitcoin-side deposit script should enforce max_fee < amount - dust_limit, (2) signers should process by minting amount - max_fee even if tiny, (3) add a reclaim/refund path for unprocessable deposits, (4) front-end UIs must validate before broadcast.

MEDIUM

M-01: Batch Deposit Failure Aborts All Subsequent Deposits

Location: complete-individual-deposits-helper

The complete-deposits-wrapper uses fold. If any individual deposit fails (replay, bad burn hash), the error propagates and all subsequent deposits in the batch are skipped.

Impact: A single invalid deposit in a batch blocks all deposits after it. Signers must carefully order/filter, or retry without the failing entry. DoS vector on deposit throughput.

Recommendation: Use a "skip on error" pattern — return (ok) with an error log for failed deposits, allowing the fold to continue.

MEDIUM

M-02: No Maximum Amount Cap on Deposits

Location: complete-deposit-wrapper

Only enforces amount >= dust-limit with no upper bound. A compromised signer could mint arbitrary sBTC in a single transaction.

Impact: Unlimited minting if signer key compromised. Inherent to trust model, but a sanity cap would limit blast radius.

Recommendation: Add a per-deposit cap (e.g., 2,100,000,000,000,000 sats = 21M BTC) as defense-in-depth.

LOW

L-01: Error Code Collision in Batch Deposits

Error encoding ERR_DEPOSIT_INDEX_PREFIX + 10 + index could theoretically collide with other error codes for large batches. In practice, batch is capped at ~500 items.

Recommendation: Use a dedicated error range (e.g., u10000 + index).

LOW

L-02: No Event Emission in Deposit Contract

The deposit contract emits no print events. Events come only from sbtc-registry.complete-deposit. A failed registry call after successful mint leaves inconsistent state with no event trail.

Recommendation: Emit a print event in the deposit contract for observability.

INFO

I-01: Pre-Clarity 4 Patterns

Uses legacy .sbtc-registry relative references. Future upgrades should adopt Clarity 4's as-contract? with explicit asset allowances.

INFO

I-02: Single Signer Principal Trust

The current-signer-principal is a single address (multisig output). Key rotation via sbtc-registry.rotate-keys. Standard sBTC design — the signer set is root of trust.

INFO

I-03: No Recipient Validation

The recipient parameter is unchecked. Signers could mint to any address including contracts or burn addresses. Low likelihood given trusted signers.

Cross-Contract Notes

  • sbtc-registry: Role-based access with bidirectional check — well-designed. map-insert for deposit-status prevents replay correctly.
  • sbtc-token: Protocol functions gated by registry — correct. No supply cap by design (sBTC = pegged BTC).

Overall Assessment

The contract is well-structured and minimal (~90 lines of logic). Main risks are protocol-level: the maxFee ≥ amount gap (H-01) causes real fund loss, batch semantics (M-01) could affect throughput, and the trust model concentrates authority in the signer set. No reentrancy risks (Clarity prevents this). The contract is solid for its scope — the critical gap is the absence of protection against unprocessable deposits.
